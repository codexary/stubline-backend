# 事后复盘草稿：回复丢失后再次提交支付，可能重复扣款

## 摘要（Summary）

财务对账发现一名买家在超时并再次提交支付后有两笔扣款。这是推动设计的事故情境，不是已复现的生产日志。最初的 `POST /payments/charge` 客户端每次尝试只调用支付方一次。买家再次按支付，或 HTTP 网关重发，属于另一次提交，仍可能造成相同的重复扣款。超时只说明调用方在期限内没有收到回复，不能证明支付方未扣款。

## 影响（Impact）

情境中，一名买家为了同一笔预期支付受到两次扣款。金额、实际发生时间、影响范围和退款状态都没有仓库证据。草稿成为正式事故记录前，必须从财务和支付方记录补齐这些事实。

## 时间线（Timeline）

- 时间未知：买家发起支付；客户端期限内没有收到支付方结果。
- 时间未知：买家或网关再次提交支付。
- 时间未知：财务对账发现同一次预期购买对应两笔支付方扣款。
- 带键支付调查：团队复现首次回复丢失和 API 幂等记录清空。记录下来的演示中，重试得到 201，支付方只扣一次，因为 key 被传到了支付方。

## 根因与触发条件（Root cause and trigger）

触发条件是不确定超时之后再次提交。带键支付实现之前的扣款路由没有跨提交共用的调用身份。最初的支付方客户端有意不自行重试扣款，但它不能控制买家或网关的行为。系统外把“没有收到回复”当作“可以安全地发起新支付”。这是系统缺口，不是某个人的失误。仓库证据无法确认情境中的第二次提交究竟来自哪条路径。

## 处理（Resolution）

针对这个情境，先核对两笔支付方 charge ID 与订单，再由财务按通常流程处理重复款项。仓库没有退款已完成的证据。带键支付实现为 `POST /payments` 增加 `Idempotency-Key`、持久化的 API 回复历史，并把 key 传给支付方。明确的扣款前拒绝会释放占有；结果不明则保留 `IN_FLIGHT` 等待核对。

## 做得好的地方（What went well）

最初的支付方客户端限制了支付方调用的时长，并避免盲目自动重试扣款。带键支付实现记录的丢失回复演示和 HTTP 测试表明，相同 key 的重试可取回 201，而支付方扣款计数仍为一。PostgreSQL 测试覆盖跨存储实例重放回复。

## 做得不好的地方（What went wrong）

旧路由没有让买家或网关的独立提交共用同一 key。API 和支付方不能原子地提交各自记录，所以扣款成功时 API 可能仍停在 `IN_FLIGHT`。演示支付方的映射是易失的。

## 幸运之处（Where we got lucky）

情境没有其他买家是否受影响的证据。测试演示成功的前提是支付方 stub 在 API 重启期间仍存活并保存 key 映射；它没有证明支付方重启后的恢复能力。
