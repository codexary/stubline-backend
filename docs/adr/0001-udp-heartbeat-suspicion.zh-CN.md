# ADR 0001：把 UDP 心跳超时视为怀疑

## 状态（Status）

草案

## 背景（Context）

Wang Hao 需要知道哪个 API 实例不再及时发送心跳。UDP 心跳实验时的 `ticketing-api` 仍是模块化单体，`health` 包包含 UDP 发送方与检测器。测试表明，停止的实例和变慢的实例在达到阈值时同样是 `SUSPECTED`；慢实例后来收到新心跳后恢复 `ALIVE`。

## 决定（Decision）

每条心跳带 instance ID 与递增序号。只在收到更新的序号时，记下检测器本地单调时钟的接收时间。经过时间达到阈值时显示 `SUSPECTED`，后来收到更新的心跳时显示 `ALIVE`。超时后的状态名称是 `SUSPECTED`，不写成 `DEAD`。在有业务流量切换规则之前，检测器只提供观察结果，不自动摘除实例。

## 考虑过的方案（Alternatives considered）

- 到期即宣告死亡：延迟、丢包和分区都可能产生同样观察，因此不采用。
- 无限等待：避免超时误报，却不能及时给值班人员信号。
- 用发送方墙上时钟计算经过时间：不同机器的时钟未必一致，因此不采用。

## 后果（Consequences）

阈值在发现延迟与错误怀疑之间取舍。重复或更旧的序号不会刷新期限。检测器保存旧序号时，重启的发送方须使用新的 instance ID。当前实现打印状态变化，不协调多个检测器的成员视图，也不切换业务流量。
