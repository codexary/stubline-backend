# ADR 0004：在 PostgreSQL 中保护座位预订

## 状态（Status）

2026-04-27 采纳。

## 背景（Context）

两个并发买家可能都通过同一座位的未受保护的可售检查。Java monitor 只保护一个进程中的一个库存对象；两个 API 进程各有自己的对象。座位状态必须共享，而且检查与修改只能产生一个赢家。

## 决定（Decision）

在 PostgreSQL 中保存可售状态和版本。`SeatInventory` 提供两种策略：`ROW_LOCK` 在事务中执行 `SELECT ... FOR UPDATE`；`OPTIMISTIC` 用可售状态和版本作条件更新，版本竞争失败后重试。本地数据库策略默认使用 `ROW_LOCK`。同步的内存实现继续供独立运行和测试使用。

## 考虑过的方案（Alternatives considered）

- 进程内 `synchronized` 方法简单，但不能协调多个副本。
- 进程内 atomic reference 能使单个 JVM 中的一次状态转换不可分割，却不能协调副本或持久保存座位。
- 单一 event loop 可以在一个进程中排列预订；持久共享状态和故障切换仍需另行设计。

## 后果（Consequences）

两种数据库策略都只允许一个买家取得一个座位。行锁可能使竞争者等待。乐观更新的版本条件可能失败，需要重新读取；冲突率高会浪费工作。座位预订实现有独立的版本冲突和重试计数器；每次条件更新失败都会增加版本冲突计数。只有后面还能再试时才增加重试计数；最后一次失败只增加冲突计数，随后方法抛错。早期实现中的座位预订与返回的订单对象尚未在同一事务中持久保存；后续订单和支付工作需要处理这一边界。
