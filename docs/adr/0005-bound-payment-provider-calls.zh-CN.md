# ADR 0005：限制支付提供方调用的等待

## 状态（Status）

2026-05-11 采纳。

## 背景（Context）

Stubline 开始调用外部支付提供方。提供方变慢或不可用时，买家请求可能一直等待。扣款回复缺失时，客户端无法确定扣款是否已执行。故障注入小项目分别观察了延迟、限速、超时和连接重置。

## 决定（Decision）

每个支付路由给出一个两秒总 deadline，每次 HTTP 尝试只使用剩余预算，完整响应体也在这个 deadline 内等待。非正预算在发送前被拒绝，订单号会做 URL 编码。`charge` 在本阶段最多发送一次；`charge-status` 最多尝试三次，并在暂时性故障之间使用指数退避和 full jitter。提供方 4xx 是明确拒绝，不重试。Resilience4j 断路器用四次调用的滑动窗口统计失败；至少一半失败时打开，默认等待三秒，然后只允许一次半开试探。记录状态变化日志。

## 考虑过的替代方案（Alternatives considered）

- 每次尝试都设置固定 timeout，会让重试和退避后的总等待超过买家预算。
- 回复丢失后重发 `charge`，可能重复已完成的业务效果。让提供方识别 idempotency key 留待带键支付实现。
- 无限制重试状态查询，会在故障时增加提供方负载，并延长买家等待。
- 不用断路器，会在持续失败时继续发送调用。使用断路器的代价是提供方提前恢复时，仍可能短暂拒绝调用。

## 后果（Consequences）

调用端限制等待完整响应的时间，并减少故障期间可避免的请求。timeout 仍不能确定扣款结果。当前 API 把未知结果和提供方明确的 4xx 拒绝都映射为 503，所以单看 API 503 无法确定结果。状态查询的重试会消耗提供方容量和 deadline。断路器属于各个 `PaymentProviderClient` 实例；`OPEN` 表示近期失败达到阈值，不证明提供方进程已崩溃。提供方的 4xx 响应也计作断路器失败。值班人员结合状态变化日志与提供方实际收到的请求判断故障。
